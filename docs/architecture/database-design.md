# LearnSphere database design

**Status:** Phase 2 identity/session, organization/access, and the Phase 4 course workflow are implemented. Collections not identified below remain design proposals. MongoDB replica set is required for transactions used by identity, organization, course, enrollment, and progress operations.

### Implemented organization/access foundation

The API currently implements `organizations`, `organizationMemberships`, `organizationInvitations`, and append-only `auditEvents`. Organization creation creates its first scoped administrator and audit record in one transaction. Memberships use a unique tenant/user index. Invitation tokens are SHA-256 hashed at rest, expire after seven days, require an authenticated account with a matching normalized email, and are accepted once. No email provider is configured: the create response says `delivery: not_configured` and returns the raw token once for the administrator to share manually. It is never persisted in plaintext or written to audit metadata.

Membership role bundles are fixed to STUDENT, INSTRUCTOR, RECRUITER, COMPANY_ADMIN, MENTOR, and ORGANIZATION_ADMIN. PLATFORM_ADMIN remains exclusively in `platformGrants` and the Phase 2 grant/MFA mechanism. Ownership transfer and audit read/export endpoints are not implemented. Organization settings are a bounded, secret-free object; the current API does not yet define a typed per-setting schema.

### Implemented Phase 4 course workflow

The API implements `courses`, `lessons`, `enrollments`, and `lessonProgresses`. Courses are organization-owned; instructors can manage their own courses and tenant administrators can manage all tenant courses. Courses and lessons move from draft to published, while courses can be archived. Enrollment and lesson completion use unique tenant-aware indexes and transactions. Content access requires both active organization membership and enrollment. Course lifecycle, enrollment, lesson authoring, and lesson-completion writes are audited. Lesson retrieval updates `lastAccessedAt` as ordinary learning activity metadata and is intentionally not a separate audit event; this avoids an audit record for every content read. Platform-wide course ownership, uploaded media, and certificates are not implemented.

## Modeling conventions

- `_id`: ObjectId; externally expose opaque string IDs. `createdAt`/`updatedAt`: BSON Date via timestamps. `deletedAt`: nullable Date only when soft deletion is required.
- `tenantId`: ObjectId referencing `organizations._id`; required for organization-owned records and absent for explicitly global or user-owned records whose access is authorized by their owner/visibility policy. Absence never implies public access. Include tenant scope in indexes and every query involving tenant-owned data.
- `ownerId`, `createdBy`, `updatedBy`: ObjectId references `users._id`; denormalized display labels are snapshots only and must not be used for authorization.
- Enumerations are validated at API and schema boundary; state transitions are application-service controlled. Monetary values use integer minor units plus ISO currency, never floating-point.
- Store references for unbounded relationships and histories. Embed small, bounded snapshots only when read patterns justify them. Do not embed messages, attempts, events, or unbounded memberships in parent documents.
- Use UTC timestamps, explicit timezone identifiers for user-scheduled local times, and immutable provider IDs for reconciliation.
- All indexes below are proposed. Validate with representative query plans/data volumes and migration tests before production.

| `platformGrants` | `userId:ObjectId`, `roleKey:string`, `permissions:string[]`, `grantedBy:ObjectId`, `reason:string`, `startsAt:Date`, `expiresAt:Date`, `revokedAt:Date?`, timestamps | `{userId:1,revokedAt:1,expiresAt:1}`; `{expiresAt:1}`. User controls field visibility. |
| `accountRecoveryRequests` | `userId:ObjectId`, `tokenHash:string`, `createdAt:Date`, `expiresAt:Date`, `usedAt:Date?`, `requestState:string` | Unique token hash; `{userId:1,createdAt:-1}`; TTL only after approved retention policy. Issue through a real configured email provider, single-use, rate-limited, and non-enumerating; successful recovery revokes sessions. |
| `auditEvents` | `tenantId:ObjectId?`, `actorId:ObjectId?`, `action:string`, `resourceType:string`, `resourceId:string?`, `requestId:string`, `occurredAt:Date`, `metadata:object` | `{tenantId:1,occurredAt:-1}`, `{actorId:1,occurredAt:-1}`, `{resourceType:1,resourceId:1,occurredAt:-1}`. Append-only application policy; redact sensitive payloads. |

Platform-wide admin grants should be separately controlled/audited; ordinary organization role bindings never imply platform administration. Consider keeping authorization role definitions in code/config for platform permissions and tenant-scoped custom role definitions only when customer demand requires them.

Role bindings are not exclusive: a user may hold several role bundles in a tenant, and different bundles across tenants. The server unions only active grants within the current scope, then still checks permission + resource relationship/ownership + tenant + consent + resource state. Platform grants are independent. Require MFA for COMPANY_ADMIN, ORGANIZATION_ADMIN, and PLATFORM_ADMIN privileged sessions; scope and audit break-glass support access.

## Relationships and ownership

- `users` are global identities. Organization-specific status and authorization live in `organizationMemberships`; never infer membership from a profile, email domain alone, or a global role label.
- `organizations` is the canonical identity for institutions, companies, and programs. Recruiters and company administrators are organization memberships; do not create a second company identity or membership model.
- Organization-owned resources carry `tenantId`. The owner module enforces tenant match on every lookup. Child tenant IDs are derived from the authorized parent (course, project, job, conversation, etc.); reject a request if any child reference's owner/tenant differs. Never trust a client-supplied tenant ID. Shared/public items have explicit visibility and controlled cross-tenant publication; null tenant does not mean unrestricted.
- References are ObjectIds and validated by owning services. Avoid MongoDB populate chains in hot paths; return purpose-built projections.
- A global course definition can be listed by many `courseCatalogEntries`; each entry is owned by exactly one organization and controls only discoverability/policy in that catalog. An organization may also own a separate course definition. Catalog membership does not reveal another tenant's progress or roster.
- `enrollments` are scoped by origin: public/global enrollment has no tenant and is unique by `(courseId,userId)`; institution-originated enrollment carries that institution's tenant and is unique by `(tenantId,courseId,userId)`. Partial unique indexes separate those cases. The same learner may therefore have separate organization-scoped learning records for the same global course; records are not merged or disclosed across tenants by default. A future explicit learner-approved portability flow may expose selected completion evidence, not raw grades/progress, according to policy.
- Institutions administer only their tenant-scoped enrollments, cohorts, submissions, and reports. Learners can export their own records across scopes; an organization export includes only its tenant records and approved shared artifacts. Profile fields remain user-controlled. Contracts and applicable law determine controller/processor responsibilities.
- Application profile snapshots preserve what was shared at submission time; candidate edits do not silently alter the historical application record.
- Assets are owned by a user or organization and referenced by domain records. Deletion checks references, retention, legal hold, and derived renditions before object removal.
- Payment provider events and order ledger states are reconciled against provider records; webhook arrival order is not assumed.
- `offers` are the sole authoritative purchasable price records; `courses` contain no price. The server resolves an active offer and approved checkout policy, computes the amount, and snapshots it into an immutable order line. A client-supplied total is ignored. Payment attempts and refunds are distinct records linked to orders and reconciled against verified provider events.
- A `courseCertificate` is issued for one completed enrollment and records issuer, evidence, issue/revocation state, and a hash of a verification token. It is not a new enrollment and public verification reveals minimal fields only.
- Mentorship availability is a bounded recurrence/rule plus exceptions; confirmed bookings are separate dated records. Prevent interval conflicts with transactional application checks and reconcile an external calendar when configured; a database unique index cannot prevent arbitrary overlapping intervals.

## Multi-tenant isolation

- Resolve tenant from a validated host, route/context, or selected active organization membership; client-supplied `tenantId` alone is never trusted.
- For nested resources, authorize the parent first, derive its tenant ID server-side, and verify every referenced child belongs to that same parent and tenant before repository access or job/socket/asset grants.
- Add tenant context to request principal and require it for tenant-owned service/repository calls. Reject missing context rather than falling back to a global query.
- Compound indexes begin with `tenantId` for tenant-filtered high-volume access. Unique constraints include tenant scope unless the identifier is intentionally global.
- Background jobs carry a tenant ID and revalidate expected ownership. Support/platform admin bypass is a separate audited policy, not an omitted filter.
- Tenant tests seed two organizations with similar IDs/data and prove no cross-read, mutation, export, socket subscription, cohort/course access, or asset access. Include global course catalog sharing and prove enrollment/progress remain tenant-private.
- Define tenant deletion, backup deletion windows, legal holds, domain verification, data residency, and cross-tenant aggregate rules before institutional launch.

## Validation, indexes, and lifecycle

- Validate structure/types with Mongoose schema constraints and API Zod schemas; validate cross-document ownership and state transitions in application services.
- Use unique indexes for idempotency and natural uniqueness, partial indexes for optional provider references, and TTL only for data whose retention policy explicitly allows automatic expiry.
- Keep bounded lists (e.g. course instructors, quiz questions under a defined maximum); separate growing relationships/events/messages into collections.
- Use cursor pagination over stable compound keys (`createdAt` + `_id`); do not use deep `skip` for unbounded feeds. Text search may require Atlas Search or a dedicated search provider; MongoDB indexes do not satisfy every marketplace search requirement.
- Roll out indexes and schema changes with backward-compatible expand/migrate/contract steps, duplicate detection, migration monitoring, and rollback plan.
- Define backup frequency, point-in-time recovery, encryption, restore testing, retention, and incident access. A backup is not verified until restore has been exercised.
- Configure bounded quotas for users/tenants, upload size/duration, retained assets, recording/rendition count, API client requests, and exports. Bound queue concurrency and retries; alert on queue age/dead letters and spend/usage thresholds. Dollar/INR limits are deployment decisions, not schema constants.

## Security and privacy

- Local password hashes use a modern adaptive algorithm in `userCredentials`; no raw passwords or reusable verification codes. Recovery tokens are single-use and hashed; successful recovery revokes active sessions.
- Browser sessions use opaque random tokens, with only a hash in `authSessions`, in Secure/HttpOnly/SameSite cookies. Rotate after login/privilege change/recovery; enforce CSRF token and Origin checks for unsafe cookie-authenticated requests; require MFA for organization, company, and platform administrators. Recovery responses avoid account enumeration and are rate-limited.
- Store provider secrets only in a secret manager; database keeps secret references. Encrypt especially sensitive fields only where justified, with key rotation and access logging.
- Do not store payment card details, raw provider secrets, signed URLs, session bearer tokens, or unnecessary full AI prompts in ordinary records.
- Apply field-level visibility and consent at query/projection time, not only UI hiding. Restrict recruiter access to applications; restrict organization staff to legitimate tenant responsibilities.
- Establish schedules for session, invitation, message, application, recording, audit, AI metadata, and analytics retention. Soft delete is not a substitute for actual deletion/cryptographic erasure obligations.
- Retention periods are approved per launch jurisdiction/contracts and must be configured before production rather than guessed in this design. Recordings are off by default, access expires before object deletion, and all renditions/transcripts share the policy. Messages and job applications are retained only for disclosed purposes and approved periods, with withdrawal/deletion behavior defined. Security audit metadata is minimized and retained only for its approved period. Encrypted backups have a bounded expiry; deletion records are replayed against restores, and physical erasure is complete when the backup window expires. Legal holds are scoped and audited.
- Uploaded assets stay private/quarantined until mandatory scan/validation succeeds; failure or scanner outage fails closed. Delete incomplete multipart uploads and orphan objects. Signed CloudFront grants are short-lived; revocation blocks new grants immediately and already-issued grants expire within a documented maximum. Deletion removes source and derived objects and handles cached copies.
- Configured webhook delivery URLs must pass SSRF checks: HTTPS, no IP literals or private/reserved IPv4/IPv6 destinations, validate all DNS answers at connection time, block cloud metadata/link-local/loopback, disable redirects or revalidate each redirect, mitigate DNS rebinding, bound response/time/redirects, and use egress controls where practical.
- Minimize audit and operational log contents; separate immutable security audit from user-generated content and analytics.

## Open data decisions

Resolve before implementation: expected tenant counts/size; identity uniqueness/account merge behavior; tenant ownership and data portability; retention durations and legal-hold policy; search/analytics vendor; hiring/learning/message/recording/AI retention schedules; cross-organization sharing/credential rules; seller-of-record and tax/refund policy; exact email/recovery provider; and India-first hosting/backup region and cross-border processing terms. Razorpay sandbox is for isolated testing only; production payment configuration is not approved by this design.
